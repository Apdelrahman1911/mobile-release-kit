## What changes

The existing twelve MAIN Access/Allow/Revoke handlers now return one additional required canonical decimal-string `permissionRevision`; each MAIN Allow requires the original `expectedPermissionRevision`. CLI Access and request DTOs are unchanged. There is no new command, AppManifest/ACL entry, permission registry, transport or clock.

The original Book counter is compared under Doc before the first source/reconcile/off-Doc cut, then rematched with every original source/Edit/Connection predicate at the final Doc/Edit/Book cut. Its checked successor is assigned **before** entering the existing fallible Inbox installer. An error after possible installation cannot reuse the old revision. Access and its counter are sampled under the same Doc linearization. Empty/cross-family Revoke, relay loss and final drain invalidate delayed Allows; overflow/poison still reaches the original Inbox STOP/close. Host/Store checks and history flush remain outside Doc/Edit/Book.

The four existing frontend controllers use their existing shared `Permission` owner. Check must actually return; Check clears old acknowledgement at entry and accepted return. A fresh explicit checkbox is required, including after external Off. The checked API/context/epoch/revision is consumed and pinned before synchronous Allow notification; post-listener checks prevent reentrant replacement. Selection/API changes withdraw it without discarding original promises. Status, failed/lost Allow and late Revoke/Allow results cannot rearm a retained unknown original. MAX disables Allow, not Stop. Only a short Check/acknowledgement help row is added to each existing panel.
