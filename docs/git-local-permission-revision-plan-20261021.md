## One MAIN wire addition and native linearization

1. Return mandatory `permissionRevision` from the existing four MAIN Access, Allow and Revoke commands, flattened beside the existing family Access fields. A small serialize-only wrapper is local to the Git native child, with only the four existing Access instantiations; it does not alter the shared service DTOs. The value is canonical decimal **string** covering full u64 (`"0"` valid, no leading zero, sign, whitespace, exponent, numeric JSON or overflow). At MAX, Access remains diagnostic but Allow cannot proceed. The family Access projection and its revision are sampled under the SAME Doc linearization, not two independently racing reads; the existing Inbox Access call is memory-only.
2. Require `expectedPermissionRevision` in all four MAIN Allow decoders. There is no missing-field/default compatibility that can rearm an old caller. The front end captures the supplied value from an actually returned original MAIN Access before the user's Allow sends anything. Native never substitutes the counter sampled on arrival.
3. At the **first Doc cut**, compare supplied revision with the same Book counter and compute its checked successor before reconciliation, source inspection or off-Doc Service calls. Release the brief Book guard before calling existing reconciliation; retain Doc, then follow the unchanged Doc/Edit/Book source ordering. All counter writers use that same Doc linearization. The second Doc/Edit/Book cut rechecks supplied==current together with every original source/selection/Connection predicate. At that final commit point assign the already checked successor in Book immediately BEFORE entering the original fallible Inbox Allow/projection, then retain the matching native Grant only on actual successful lease return. Thus every attempted install consumes N once, including an error after a possible install; a pre-mutator refusal leaves N unchanged. There is no post-install fallible wrapper, serialization or return path that can leave N reusable. This is a conservative one-use comparison, not a retry or a new permission on error.
4. Two Allows carrying N may both reach an off-Doc read, but only one can commit N→N+1; the other refuses without installing/replacing a lease. Any post-install response loss remains the original uncertain call; neither native nor UI retries with N or manufactures a replacement. Refusal before installation does not grant anything.
5. All four existing `{}` MAIN Revokes advance this **same** counter even with no lease/service, then execute the existing memory-only shared Inbox revoke. Counter overflow/poison must not skip STOP/close; MAX remains absorbing. `git_index_relay_lost` and the final drain similarly invalidate delayed Allows under Doc before the original revoke/close. Their actual callers (`GitIndexRelayGuard`, relay path failure, `android_build_relay_lost`, normal joined Quit) do not already hold Doc. No Doc/Edit/Book guard crosses Host/Store IO or `flush`.

No new timestamp, cancellation task or timer is introduced. Existing Inbox cancel, first STOP, original Git 45/55 endpoints, native receipts, ReadyReview expiry and relay/history custody are preserved, including stopping when counter advancement fails. Existing source-invalidating tick revocations retain their original source gates; they are not a new permission authority. No clearing of a retained grant/row is used as a receipt or capacity credit.

## Existing four-panel controller, no silent refresh

Reuse `service_git_permission.ts::Permission` (used only by these four panels), its single Allow/Status work slot, separate Revoke work slot and retained original API. The four family Access parsers require the new canonical string; each raw Allow API receives the expected revision as a separate immutable parameter, not as a project/draft property and not from CLI data.

An initial user **Check/Refresh permission** must actually return before Allow is enabled. Check clears prior acknowledgement at entry and at each accepted return; acknowledgement attempted while Check or Revoke is pending is rejected. A newly checked origin always needs a fresh explicit acknowledgement, including when an external Off happened after an older checkbox. The common controller privately retains that result's revision with the exact API/context and its current local epoch. It is pinned in the original Work **before synchronous listener publication**, and not replaced by a later Status/Allow/Revoke result while that Work is live. Selection/API/context changes withdraw the actionable comparison without discarding the pending original; a newly selected context needs its own joined Check. At Allow entry the comparison is consumed locally (even if listeners veto before send); new explicit Check is needed for another user choice. After callbacks re-sample the same context/API/block/epoch/Work and Revoke before invoking raw Allow once.

Revoke continues to supersede the exact older Work and retain both promises until each returns. A late Allow cannot restore permission after it; status never clears an uncertain/lost original or substitutes for Revoke/native cleanup. Canonical MAX and unknown/missing revisions disable Allow without disabling Stop. Each existing panel already has Check/Refresh and Stop controls; only concise help text is needed to explain Check→explicit checkbox→Allow, not automatic network/source reads. Normal warnings, selected actions and native recovery remain visible.
